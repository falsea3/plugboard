Why Relay

A mock server from your examples

Save real responses as examples and serve the collection on localhost. Build the frontend before the endpoint exists.

Git is the sync

Workspaces are reviewable YAML in your repo. Tokens stay on your machine and never land in the diff.

MCP, by hand

Point Relay at a Model Context Protocol server, list its tools, fill in the arguments and read the raw exchange.

Small and fast

A small app that opens in a moment and stays quick, without eating your disk or memory.

200 OK in your API client. Blocked in Chrome.

API clients aren’t browsers, so they skip the checks that break your frontend. Give Relay the page’s origin and it sends the preflight, applies the credentials rules and checks the response the way the Fetch spec says — then tells you, in one line, why the browser would refuse.

How browser emulation works

POST https://api.example.com/v1/orders

A usual API client 200 OK { "id": "ord_8123", "status": "created" } Looks fine. Ship it.
Relay, as the browser Blocked CORS preflight failed: Access-Control-Allow-Headers does not include "authorization" for origin https://app.example.com What your users would have hit.

  1. CORS preflight

    Sent when the method or headers are not safelisted. Status, methods, headers and Max-Age are validated — no redirects, no cookies.

  2. Credentials mode

    Cookies are held back cross-origin unless you include them, and a wildcard origin is rejected the moment you do.

  3. CSP connect-src

    Paste the page’s policy. Relay blocks the request before it connects and checks every redirect again.

  4. Origin and fetch metadata

    A browser User-Agent, Origin and Sec-Fetch-Site, -Mode and -Dest, worked out from scheme, host and port.

Moving from Postman?

Drop in your export and keep going — your pm.* scripts keep running.

Migration guide

From Postman

  1. Export the collection as v2.1 — and your environments, if you use them.
  2. Click the import icon in the sidebar, or drop the file onto it.
  3. Press Send. Your pm.* scripts run as they are.

What comes along

  • Folders
  • Requests and bodies
  • Auth, OAuth 2.0 included
  • AWS SigV4
  • pm.* scripts
  • Environments
  • {{variables}}
  • Saved responses → examples

Monitors and Flows stay behind — the CLI runner and the local mock server cover the same ground.

From Insomnia

  1. Preferences → Data → Export Data, as Insomnia v4 (JSON).
  2. Import the file — Relay works out the format on its own.
  3. Swap any custom template tags for variables.

What comes along

  • Workspaces → collections
  • Folders
  • Requests and auth
  • Environments
  • {% tags %} → {{variables}}

Custom template-tag plugins come in as plain text; move them into a variable or a pre-request script.

From Bruno

  1. Pick your Bruno or OpenCollection export.
  2. Import it from the sidebar.

What comes along

  • Folders
  • Requests
  • Saved examples

From OpenAPI

  1. Paste the spec’s URL — or pick the file.
  2. Relay builds a collection from it.

What comes along

  • Every endpoint as a request
  • Examples from the spec
  • Swagger too

From HAR

  1. In your browser’s DevTools, Network → Save all as HAR.
  2. Import it — every captured call becomes a request.

What comes along

  • Captured requests
  • Responses as examples

From curl

  1. Copy a curl command from the docs or DevTools.
  2. Paste it into the URL field. That’s it.
curl -X POST https://api.example.com/v1/orders \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"sku":"KB-75","qty":1}'

What comes along

  • Method and URL
  • Headers
  • Body

And back again: export any collection to Postman v2.1. Your data is never trapped.

The same tests, in CI. No second tool.

The desktop app is the CLI. relay run executes the workspace from your repo with the same requests, pm.* scripts and collection auth — and a failed assertion fails the build. JUnit and JSON reporters included.

Run Relay in CI
tests.js 
// tests run in the app and in CI alike
pm.test("status is 200", () => pm.response.to.have.status(200))
pm.test("has an id", () =>
  pm.response.to.have.jsonSchema({ type: "object", required: ["id"] }))
CI 
$ relay run ./workspace --env CI

Check what you download

Every release ships SHA-256 checksums and signatures, and the in-app updater refuses a build that fails either check. To check an installer yourself, put it next to SHA256SUMS.txt from the same release and run:

Older versions and their checksums are on GitHub.

macOS shasum -a 256 -c SHA256SUMS.txt --ignore-missing
Linux sha256sum -c SHA256SUMS.txt --ignore-missing
Windows Get-FileHash .\installer.exe -Algorithm SHA256

What leaves your machine

The complete list. There is no analytics endpoint, so there is nothing to opt out of.

  • The APIs you call

    Only when you send a request or run a collection.

  • GitHub, for the update check

    The one request Relay makes without being asked.

  • Your browser, if you pair cookie sync

    Loopback only, off until you turn it on, approved with a six-digit code.

Where your data lives

On your disk, in formats you can open without the app.

  • An encrypted profile

    Your local profile and its secrets are encrypted at rest with AES-256-GCM. The key is kept in the OS credential store when one is available.

  • Workspaces you can commit

    Git-backed workspaces are readable YAML. Secret values are swapped for local placeholders, so they never reach the repo.

FAQ

Short answers to what people ask most.

Ask on GitHub
01 Can I import my Postman collections?

Yes — Postman, Insomnia, Bruno/OpenCollection, OpenAPI/Swagger, HAR and cURL. Scripts that use the pm API keep working.

02 Can I run requests in CI?

Yes. relay run executes requests and their tests from a workspace folder, with data-driven iterations and JUnit output.

03 Where are my requests stored?

On your computer. Git-backed workspaces are plain YAML; secret values are replaced with local placeholders.
